# Week1 概念详解

## Chat API 是无状态的

每次 API 调用都是一次独立请求。模型只看这次请求里的 `messages`，不会自动读取上次对话。

```text
第 1 轮：system + user1 → assistant1
第 2 轮：system + user1 + assistant1 + user2 → assistant2
```

如果第 2 轮只发 `user2`，模型就不知道第 1 轮发生过什么。

## `messages` 是应用侧状态

`messages` 不是“模型记忆”，而是应用维护的一段上下文列表。多轮对话的核心就是：

```text
append user → 请求模型 → append assistant → 下一轮重发完整 messages
```

`/clear` 的本质是重置这个列表，所以模型会“失忆”。

## 四种 role

| role | 来源 | 作用 |
| --- | --- | --- |
| `system` | 开发者 | 规则、身份、格式、边界 |
| `user` | 用户 | 当前任务或问题 |
| `assistant` | 模型 | 模型输出，可能是自然语言，也可能带 `tool_calls` |
| `tool` | 代码 | 工具执行结果，必须对应某个 `tool_call_id` |

## token 不是字数

token 是模型分词后的单位，用于计费和上下文长度限制。中文、英文、符号都可能被切成不同粒度。

要点：

- system prompt、历史消息、角色模板都会消耗 prompt token。
- completion token 是模型生成的部分。
- 多轮越长，prompt token 通常越多。

## Function Calling 的本质

Function Calling 不是模型执行函数，而是模型输出结构化调用意图：

```text
assistant:
  tool_calls:
    - name: get_weather
      arguments: {"city": "北京"}
```

随后应用代码负责：

1. 解析 `arguments`。
2. 找到对应 Python 函数。
3. 执行函数。
4. 把结果作为 `role: tool` 写回 `messages`。
5. 再请求模型生成最终回答。

## `tools` schema 是工具说明书

模型能不能选对工具，很大程度取决于 schema：

| 字段 | 影响 |
| --- | --- |
| `name` | 模型可调用的工具名 |
| `description` | 模型判断何时调用 |
| `parameters` | 模型如何填参数 |
| `required` | 哪些参数必须提供 |

Python 函数签名和 schema 不会自动同步，学习阶段要手动保持一致。

## 工具错误也要变成 observation

工具执行失败时，不要让程序直接崩溃。更好的做法是返回错误字符串：

```text
错误：城市不能为空
错误：除数不能为 0
错误：未配置 API Key
```

这样模型下一轮才能基于错误信息改正、重试或向用户说明失败原因。
