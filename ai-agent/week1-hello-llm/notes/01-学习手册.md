## Day 1-2：第一次 LLM 调用

### 目标

- 跑通 `hello.py`，确认 API key、base url、model 配置正确。
- 理解 `system` / `user` / `assistant` 三种角色。
- 观察 token usage，建立“token 不是字数”的直觉。

### 运行

```bash
cd ai-agent
source .venv/bin/activate
python week1-hello-llm/code/hello.py
```

### 观察

- 终端是否打印模型回答。
- `usage.prompt_tokens`、`completion_tokens`、`total_tokens` 分别是多少。
- 改 system prompt 后，回答风格是否变化。
- 是否能复述这次请求的输入、输出和 token 成本。

### 关键结论

- Chat API 是无状态的：下一轮不会自动记得上一轮，应用必须把历史 `messages` 再发一次。
- `system` prompt 也是输入 token 的一部分，会影响行为边界和输出风格。
- completion token 和字符数不是一回事，中文、标点、英文片段都会按 tokenizer 切分。

## Day 3-4：多轮对话

### 目标

- 跑通 `chat.py`，观察 `messages` 如何累积。
- 修改 system prompt、temperature、few-shot 示例，观察输出差异。
- 用 `/clear` 验证上下文确实存放在本地 `messages` 中。

### 运行

```bash
cd ai-agent
source .venv/bin/activate
python week1-hello-llm/code/chat.py
```

### 实验

- 连续问两轮，让第二轮引用第一轮内容。
- 输入 `/clear`，再问上一轮相关问题。
- 用 `/temp 0` 和 `/temp 1.2` 对比稳定性。
- 可选：在初始化 `messages` 里加入 few-shot 示例。

### 关键结论

- 多轮对话的本质是不断追加 `user` / `assistant` 消息，然后把完整历史重新发送。
- 聊得越久，`total_tokens` 通常越高，因为历史上下文变长了。
- `/clear` 后模型无法记住之前内容，说明“记忆”来自应用侧状态，不是 API 自动保存。
- temperature 影响输出随机性，但不能代替清晰的任务说明。

## Day 5-7：Function Calling

### 目标

- 跑通 `function_calling_demo.py`。
- 理解 `tools` schema、Python 函数、`dispatch_tool` 的分工。
- 看清两轮请求：模型选择工具 → 代码执行工具 → 模型生成最终回答。

### 运行

```bash
cd ai-agent
source .venv/bin/activate
python week1-hello-llm/code/function_calling_demo.py
```

### 观察

- 第一轮 assistant 是否返回 `tool_calls`。
- `function.name` 和 `function.arguments` 是什么。
- 代码如何 dispatch 到真实函数。
- 第二轮为什么要加入 `role: tool`。
- 工具 observation 是否足够清楚，模型能否基于它生成最终回答。

### 关键结论

- LLM 不会真的调用函数，它只输出 `tool_calls`，真实执行发生在应用代码中。
- 工具描述是模型选择工具的主要依据，描述含糊会直接影响调用质量。
- 工具执行结果必须以 `role: tool` 写回 `messages`，模型才能基于 observation 继续回答。
- 第二轮请求仍要带上 `tools`，因为模型可能继续判断是否需要工具。
