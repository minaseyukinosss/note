# Week1 总结：LLM 调用与 Function Calling

## 本周目标

- 跑通最小 LLM 调用，理解 Chat API 的输入输出。
- 理解 `messages` 是应用侧维护的状态，不是模型自己记住了对话。
- 跑通 Function Calling 两轮协议，为 Week2 的 ReAct 循环打底。

## 本周脉络

```text
Day 1-2  hello.py
    单次请求：system + user → assistant
Day 3-4  chat.py
    多轮：应用维护 messages，每轮重发完整历史
Day 5-7  function_calling_demo.py
    工具调用：assistant(tool_calls) → code 执行工具 → tool observation → assistant(content)
```

Week1 的重点不是“让模型变聪明”，而是看清协议边界：模型只读你发过去的上下文，只输出文本或结构化 tool call；真实函数调用、状态保存、错误处理都在你的代码里。

## 核心收获

1. **Chat API 无状态**：服务端不保存上一轮对话；多轮靠你的程序把历史 `messages` 全量带上。
2. **角色有边界**：`system` 定规则，`user` 给任务，`assistant` 是模型输出，`tool` 是工具执行结果。
3. **token 不是字数**：计费和上下文限制看 token；角色模板、system prompt、历史消息都会占 prompt token。
4. **Function Calling 是协议，不是执行**：模型输出 `tool_calls`；Python 的 `dispatch_tool` 才执行真实函数。
5. **工具 schema 是给模型看的 API 文档**：`name`、`description`、`parameters` 会直接影响模型是否选对工具。

## 常见错误

| 现象 | 原因 / 修正 |
| --- | --- |
| 第二轮接不上上一轮 | 没把上一轮 `assistant` 写回 `messages` |
| `/clear` 后模型失忆 | 正常现象；`messages` 被重置了 |
| 模型没有调用工具 | 工具 description 不清楚，或用户问题不需要工具 |
| 工具返回后模型仍不知道结果 | 忘了 append `role: tool`，或缺少 `tool_call_id` |
| token 越聊越贵 | 每轮都重发完整历史；后续要学窗口、摘要和记忆策略 |

## 验收自测

1. **多轮对话靠什么实现？**  
   靠应用维护并重发完整 `messages`，不是 API 自动保存会话。

2. **Function Calling 的两轮分别做什么？**  
   第一轮模型选择工具和参数；代码执行工具后把 observation 写回；第二轮模型基于 observation 生成最终回答。

3. **模型会执行 Python 函数吗？**  
   不会。它只输出结构化调用意图，真实执行在你的代码里。

4. **为什么工具 description 很重要？**  
   模型靠 description 判断何时调用、调用哪个工具、参数大概该怎么填。

## 与 Week2 的衔接

Week1 的 `function_calling_demo.py` 是固定两轮。Week2 会把这套协议放进 `for` / `while` 循环：

```text
请求模型 → 有 tool_calls 就执行工具 → 写回 observation → 再请求模型
```

当模型不再返回 `tool_calls`、直接返回最终 `content` 时，ReAct Agent 结束。
