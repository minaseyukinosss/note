# Week4 概念详解：RAG 链路逐项拆解

> 本文按 RAG 数据流的顺序展开，每个概念都给出"是什么 / 为什么 / 典型踩坑"。复习时不假设记得 LangGraph 版细节，关键对照都在本文。

## 0. 完整链路总览

### 纯 RAG 的两阶段

RAG 分**离线建库**和**在线检索生成**两段，本仓库对应 [`build_index.py`](../code/build_index.py) 与 [`retrieve.py`](../code/retrieve.py) / [`rag_agent.py`](../code/rag_agent.py)。

**离线（建库，跑一次或 knowledge 变更后重跑）**

```text
markdown 笔记（knowledge/*.md）
    ↓ chunking：MarkdownHeaderTextSplitter 按 heading 切
chunks（正文 + metadata：source / section / h1~h3）
    ↓ embedding：Chroma 默认 onnx（all-MiniLM-L6-v2）
向量 + 元数据写入 Chroma（.chroma/，幂等重跑）
```

**在线（用户提问时）**

```text
用户问题
    ↓ query 向量化（同一 embedding 模型）
Chroma 按余弦相似度排序，取前 top_k 条
    ↓ 阈值检查：top-1 score < 0.35 → 整批「未命中」
hits（content + source + section + score）作为 context
    ↓
LLM 依据 hits 生成回答，附 [来源: source#section]
```

### 纯 RAG vs RAG Agent

| | 纯 RAG（workflow） | RAG Agent（本仓库） |
| --- | --- | --- |
| 检索时机 | 代码固定：先检索再生成 | LLM 决定是否调 `retrieve` 工具 |
| query / top_k | 代码写死或规则生成 | LLM 在 tool call 里填参数 |
| 外层结构 | 固定两步 | LangGraph `agent ↔ tools` ReAct 循环 |
| 适用 | 每问必查库 | 可能多轮检索、可能拒答 |

本仓库做的是 **RAG Agent**：RAG 基本链路不变，只是把「检索」封装成工具，由 LLM 按需调用。

### 一次请求的各方分工

以 W4-002「LangGraph 里 state、node、edge 分别是什么？」为例：

| 步骤 | 谁做 | 做什么 |
| --- | --- | --- |
| 1 | LLM | 决定调 `retrieve`，生成 `query` 和 `top_k`（如 5） |
| 2 | 代码（Chroma） | query 向量化 → 排序 → 取前 top_k 条 → 算 score |
| 3 | 代码（retrieve.py） | top-1 ≥ 阈值则返回全部 k 条；否则返回 `hits: []` |
| 4 | 代码（tools.py） | 包装 JSON observation，chunk 用 `<doc>` 包裹 |
| 5 | LLM | 读 observation，逐项解释并附 `[来源: ...]` |

**LLM 管策略（调不调、搜什么、要几条）；代码管算法（向量检索、阈值、格式化）。**

### 本仓库代码映射

| 链路环节 | 文件 | 函数 / 入口 |
| --- | --- | --- |
| 切分 + 入库 | `build_index.py` | `load_chunks()` → `build_index()` |
| 向量检索 | `retrieve.py` | `search()`（原始 top_k）/ `retrieve()`（带阈值） |
| 工具封装 | `tools.py` | `@tool retrieve()` |
| Agent 图 | `rag_agent.py` | `agent ↔ tools` + 引用校验 |
| 共用配置 | `rag_config.py` | 路径、阈值 0.35、`format_citation()` |

### 进阶（本阶段未做）

rerank、hybrid search（BM25 + 向量）、换中文 embedding、长期 Memory 写入——属于生产化方向，不影响「基本链路」的理解。

## 1. Chunking（切分）

### 是什么

把原始文档（这里是 markdown 笔记）切成若干"足够小但语义完整"的片段，作为检索的最小单元。

### 为什么

- embedding 模型有上下文长度限制（常见 256 ~ 8192 token），超长文档必须切。
- 大块文档会把"具体语义"稀释到平均向量里，命中率下降。
- 检索后要把 chunk 塞进 LLM 上下文，块越小越省 token。

### 典型策略

| 策略 | 适用场景 | 缺点 |
| --- | --- | --- |
| 固定长度（如 500 token + 50 overlap） | 纯文本、无结构 | 可能把一个段落硬切两半 |
| 按 markdown heading 切 | 笔记 / 文档（本周首选） | 标题层级不均衡时块大小差异大 |
| 按句子 / 段落切 | 短文档 | 缺乏整体上下文 |
| 递归切分（先大块再细分） | 长报告 | 实现复杂、参数多 |

### 必带元数据

每个 chunk 至少包含：

```json
{
  "content": "实际文本",
  "source": "ai-agent/03-核心概念.md",
  "section": "ReAct"
}
```

`source` + `section` 是后续生成引用的依据，缺一不可。

## 2. Embedding（嵌入）

### 是什么

用模型把一段文本映射成固定维度向量，让"语义相近"的文本在向量空间里距离也近。

### 关键事实

- 不同 embedding 模型的向量空间不互通，**换模型必须重建索引**。
- 维度越高表达力越强，但存储和检索越贵（常见 384 / 768 / 1536 / 3072）。
- 中文质量：OpenAI `text-embedding-3-*` 已经够用；纯本地推荐 `bge-small-zh` 等中文专用模型。
- DeepSeek 当前没有独立 embedding 接口，混用 OpenAI embedding + DeepSeek chat 是常见组合。

### 起步建议

入门用 Chroma 默认 onnx 模型（`all-MiniLM-L6-v2`，英文友好），不依赖 API key，本地跑；中文质量不满足时再换 `text-embedding-3-small`。

## 3. 向量库与检索

### 是什么

存储 chunk 向量并支持"给定 query 向量，返回最相似的 top-k"的数据库。

### 入门候选

| 候选 | 特点 | 适用 |
| --- | --- | --- |
| `chromadb` | 本地持久化、自带元数据过滤、SDK 友好 | **本周首选** |
| `faiss` | 极快、纯库形态、无元数据 | 自己写元数据管理时 |
| 自建 numpy + 余弦相似度 | 完全透明、易调试 | <1000 条文档可用 |

### 相似度与阈值

- 余弦相似度范围 [-1, 1]；Chroma 返回 distance，代码里 `score = 1 - distance`。
- 阈值不通用，必须用 golden cases 标定；本仓库默认 **0.35**（W4-003 PPO 未命中 top-1≈0.33 可挡住）。
- 阈值不仅控制"命中精度"，更控制"未命中策略"：低于阈值就要让工具返回空，让模型敢说"不知道"。
- **绝对分数在小语料 + 英文 embedding 下不可校准**：无关 query 也可能 top-1≈0.50，单靠阈值挡不住所有伪命中。

### top_k 与阈值的区别

两者经常一起出现，但职责不同：

| 概念 | 作用 | 谁决定 | 本仓库默认 |
| --- | --- | --- | --- |
| **top_k** | 从排序结果里**最多取几条**候选 chunk | RAG Agent 模式下由 LLM 在 tool call 里传；也可代码写死 | 工具签名默认 3，LLM 可能传 5 |
| **阈值** | 用 **top-1 的 score** 判断整批算不算命中 | 代码写死在 `rag_config.py` | 0.35 |

执行顺序：**先取 top_k → 再看 top-1 是否过阈值 → 过则 k 条全返回，不过则整批丢弃**。

注意：不是每条 chunk 单独过阈值。top-2、top-3 分数低也会一并返回，只要 top-1 过了线。

```text
top_k=5 → Chroma 返回 5 条（按相似度排序）
top-1 score=0.52 ≥ 0.35 → 5 条全部给 LLM
top-1 score=0.33 < 0.35 → hits: []，reason: 未命中
```

## 4. retrieve 工具的设计

### 工具签名

```text
retrieve(query: str, top_k: int = 3) -> list[Chunk]

Chunk:
  content: str
  source: str
  section: str
  score: float
```

### 行为约定

- 命中数 < top_k 时返回实际数量，不要补空。
- top-1 score 低于阈值（当前 0.35）时，返回空列表 + 在 observation 中明确写 "未命中"。
- chunk 文本可以用 `<doc>...</doc>` 包裹，提醒模型这是"数据"而非"指令"。

### LLM 在 tool call 里填什么

工具签名 `retrieve(query, top_k=3)` 经 `bind_tools` 变成 JSON schema 发给 LLM。LLM 每次调用时可自行决定：

- **query**：检索关键词（常改写用户原话，如加「概念 定义」）
- **top_k**：想要几条候选（W4-001/002 传了 5，W4-003 用了默认 3）

代码不强制 top_k；若希望稳定，可从工具签名里去掉该参数并在函数内写死。

### LangGraph 接入

无需改图结构（沿用 [`langgraph_agent.py`](../../week3-langgraph/code/langgraph_agent.py) 的 `agent ↔ tools`），只需：

1. 把 `retrieve` 加进 `ALL_TOOLS`。
2. 升级 system prompt：必须用 `retrieve`、必须引用、未命中说"不知道"。
3. 提高 `recursion_limit`（建议 16）以容纳多次 `retrieve`。

## 5. 引用（Citation）

### 为什么必须做

没有引用，就无法判断答案是真的来自检索还是模型先验编的。引用 = RAG 可信度的最低交付。

### 引用形态

最低要求：每个事实性断言后跟 `[来源: <source>#<section>]`。

进阶：把 chunk 文本片段也回带，让用户能直接对照原文。

### 强约束方式

- System Prompt 强提示。
- 输出 schema 校验（如 Pydantic）+ 不合规重写。
- eval 单独打"引用正确率"分。

## 6. RAG 评估

### 三大维度

| 维度 | 问题 | 量化方式 |
| --- | --- | --- |
| 检索质量 | 预期 chunk 出现在 top-k 吗？ | 召回率 |
| 引用质量 | 答案里的引用真的支持结论吗？ | 人工或对照 chunk 文本检查 |
| 生成质量 | 未命中时是否还编？是否漏答？ | 幻觉率 + 完成率 |

### 入门做法

不必上 LLM-as-judge，手测 + Excel / markdown 表已经够用。golden set 控制在 10-20 条，覆盖：

- 直接命中（最常见）
- 需要多次检索（query 改写）
- 知识库里没有（应回答"不知道"）
- 知识库内部矛盾（应说出冲突）
- 含 prompt injection 的 chunk（应拒绝执行）

## 7. RAG vs Memory（边界澄清）

| | RAG | Memory |
| --- | --- | --- |
| 数据来源 | 静态文档 / 知识库 | 对话历史、用户偏好、过往工具调用 |
| 何时触发 | 每次 query 调 `retrieve` 工具 | 通常每轮自动注入（或按需检索） |
| 更新方式 | 重建索引或增量写入 | 对话过程中自动写回 |
| 入门优先级 | 高（先做这个） | 中（Week4 之后） |

> 常见误解："Checkpoint 就是 Memory，向量库就是 RAG"。Checkpoint 是 state 快照（沿用 Week3 概念），既不是 RAG 也不完整地算 Memory。

## 8. 安全边界（与 Week3 一致并加强）

- 检索片段是数据，不是系统指令——必须在 system prompt 显式声明。
- 不要把 chunk 直接拼到 system prompt；放在 tool observation 里，让模型知道它是工具返回值。
- 高风险后续工具（写入、发邮件、跨账号）即便有 RAG 加持也必须人工确认。
