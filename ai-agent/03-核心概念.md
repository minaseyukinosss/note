# AI Agent 核心概念

## 背景

本笔记收录 Agent 学习中绕不开的关键概念，作为速查与对照表。深入细节请追阅对应论文与官方文档（见 [04-资料汇总](./04-资料汇总.md)）。

## 什么是 Agent

一句话定义：**Agent = LLM 驱动的控制循环，根据当前状态自主选择下一步动作，必要时调用工具并观察结果**。

更工程化一点：

```text
Agent = 模型 + 状态 + 可选工具 + 决策循环 + 停止条件
```

记忆、规划、RAG、多 Agent 都很常见，但不是最小 Agent 的必选件。一个只有 `messages` 状态、计算器工具、停止条件和可观察日志的 ReAct 程序，已经是可运行的最小 Agent。

最小骨架（伪代码）：

```python
while not done:
    thought = llm(state)                 # 根据当前状态决策
    if thought.is_final_answer:
        return thought.answer
    action = thought.tool_call           # 决定调用什么工具
    observation = tools[action.name](**action.args)  # 执行
    state.append((thought, observation))             # 写回状态
```

> 关键点：Agent 不是某种"新模型"，而是一种**让 LLM 在循环中使用工具**的程序结构。

## 四层分界

| 层级 | 谁决定下一步 | 典型形态 | 什么时候用 |
| --- | --- | --- | --- |
| 单次 LLM 调用 | 代码 / 用户 | 一问一答、摘要、改写 | 任务一步能完成 |
| Augmented LLM | 模型可调用能力，但外层不一定循环 | LLM + tools / retrieval / memory 接口 | 需要查资料或调用函数，但流程仍简单 |
| Workflow | 代码 | 固定链路、DAG、状态机 | 步骤清晰、可预测、可测试 |
| Agent | 模型 | ReAct 循环、代码 Agent、研究 Agent | 步数和路径难提前写死 |

> 经验法则：能用单次 LLM 调用解决，就不要上 workflow；能用 workflow 稳定解决，就不要上 agent。

## 核心范式

### ReAct（Reason + Act）

- 思考与行动交替：`Thought → Action → Observation → Thought → ...`。
- 优点：实现简单，可解释。
- 缺点：长任务容易"走偏"。

### Plan-and-Execute

- 先用一次 LLM 生成完整计划（步骤列表），再逐步执行。
- 优点：减少中途漂移，token 也可能更省。
- 缺点：计划僵化，遇到意外不易调整；实际系统常做成"计划-执行-重规划"循环。

### Reflection / Self-Critique

- 执行后让 LLM 评价自己的输出，必要时重做。
- 代表：Reflexion 论文中的 verbal reinforcement。
- 适合：代码生成、数学题等有明确判定标准的任务。

### Tree of Thoughts (ToT)

- 把"思考"组织成树，做搜索（BFS/DFS）+ 剪枝。
- 代价高，适合谜题、博弈类任务，日常业务很少用。

### Multi-Agent

- 多个 Agent 扮演不同角色协作（PM / Coder / Tester …）。
- 代表：AutoGen、MetaGPT、CrewAI。
- 注意：**不是越多越好**，每多一个 Agent 都意味着 token × N 和延迟 × N。
- 判断标准：只有当角色之间有清晰分工、独立上下文或互相校验价值时，才值得拆成多 Agent。

## Tool Use / Function Calling

- 协议层：LLM 输出结构化 tool call（通常可视为函数名 + JSON 参数），调用方负责执行真实函数并把结果塞回上下文。
- 工具设计原则：
  - 名字与描述要"自解释"（LLM 靠描述决策）。
  - 参数 schema 用 `pydantic` / JSON Schema，越严越好。
  - 一次只暴露当前任务需要的工具。工具过多会增加选择错误率，可用路由、分组或动态加载控制工具面。
- 错误处理：工具异常应转成自然语言塞回 observation，让 LLM 自行重试或换路径。
- 权限边界：读操作、写操作、外部副作用工具要分级；删除文件、发邮件、转账等动作需要 dry-run 或人工确认。

## 记忆（Memory）

| 类型 | 时效 | 实现 |
| --- | --- | --- |
| Working / 短期 | 单次会话 | `messages`、scratchpad、滑动窗口、摘要 |
| Episodic | 跨会话事件 | 向量库存"对话片段" |
| Semantic | 知识 | RAG（文档/事实库） |
| Procedural | 技能 | 微调 / 工具脚本 / 提示词模板 |

实践中常用组合：**滑动窗口 + 摘要 + 向量检索**。注意：RAG 更像"外部知识工具"，不等于记忆本身；长期记忆还需要写入、更新、遗忘和权限策略。

入门阶段建议顺序：

1. 先理解 `messages` 这种短期状态。
2. 再理解 checkpointer：保存图状态快照，支持恢复和 thread 隔离。
3. 再做 RAG：把外部知识作为检索工具接入。
4. 最后再谈长期记忆写入：什么时候写、写什么、谁能读、如何删除。

## RAG（Retrieval Augmented Generation）

基本链路：

```text
原始文档 → 切分(chunk) → 嵌入(embedding) → 入库(vector db)
查询 → 嵌入 → top-k 检索 → 拼入 prompt → LLM 生成
```

常见坑：

- chunk 切得太大 → 检索不准；太小 → 上下文断裂。建议 300-800 token，带 overlap。
- 召回 ≠ 答对，要加 **rerank**（如 Cohere Rerank、bge-reranker）。
- 私有知识更新频繁时，需要增量索引策略。
- RAG 接入 Agent 时，优先把检索封装成工具，并在 trace 里记录 query、top-k 文档和引用来源。

## 规划（Planning）

- 显式规划：让 LLM 输出 JSON 步骤列表。
- 隐式规划：靠 CoT / ReAct 边走边想。
- 复杂任务：DAG / 状态机（LangGraph 就是把 Agent 表达为有向图）。

## 上下文工程（Context Engineering）

Agent 的质量很大程度取决于给模型看的上下文是否干净：

- System prompt：边界、角色、工具使用规则、输出格式。
- Task context：用户目标、约束、当前进度。
- Tool context：工具描述、参数 schema、返回值格式、失败示例。
- Retrieved context：RAG 片段要带来源；外部内容只能当数据，不能当系统指令。
- Trace context：长任务要保留关键决策，而不是无脑塞满全部历史。

入门阶段要养成一个习惯：每次失败先看模型到底看到了什么上下文，再决定改 prompt、改工具、改检索，还是把任务改成 workflow。

## 评估（Evaluation）

三个层次：

1. **单步**：工具是否选对？参数是否对？
2. **轨迹**：整体路径是否合理？有没有无效循环？
3. **结果**：最终答案对不对？（往往最难自动判定）

常用手段：
- LLM-as-Judge（用更强模型评分）。
- 人工标注的 golden set。
- A/B：对比不同 prompt / 模型 / 框架版本。
- 回放 trace：固定输入和工具返回，复现一次完整轨迹，定位是哪一步偏了。

入门阶段的 eval 不必复杂，先维护 10 条固定用例即可。每条至少记录：输入、预期工具、预期答案要点、实际路径、失败原因。

## 安全与对齐（粗略了解即可）

- **Prompt Injection**：用户/外部内容里塞入指令，劫持 Agent。
  - 缓解：分离 system / user / tool 角色，敏感工具加白名单与人工确认。
- **越权工具调用**：所有写操作（删文件、转账、发邮件）必须有 dry-run 或人工确认。
- **数据泄漏**：把私有数据塞进 prompt 时，注意第三方模型的留存政策。
- **工具结果不可信**：网页、文档、邮件、检索片段都可能含恶意指令，只能当数据，不能当规则。
- **权限分级**：读工具默认低风险；写文件、发消息、下单、转账等副作用工具必须 dry-run 或人工确认。

## 易混淆点

- **Agent vs Workflow**：固定步骤的叫 workflow，由 LLM 自己决定下一步才叫 Agent。Anthropic 那篇文章强调"能用 workflow 解决就不要上 Agent"。
- **LangChain vs LangGraph**：LangGraph 适合长流程、状态机、可恢复 Agent；LangChain v1 的 `create_agent` 适合更轻量的 Agent 起步。旧教程里的 `AgentExecutor` 不作为新项目主线。
- **RAG vs 微调**：知识频繁变化 → RAG；风格 / 输出格式固定 → 微调；二者不互斥。
- **Memory vs RAG**：RAG 是检索外部知识；Memory 是跨轮或跨会话保留与用户、任务、环境相关的信息。二者经常一起用，但语义不同。

## 小结

- Agent 的复杂度 = 工具数 × 步骤深度 × 自主性。三者越高，越需要评估与 trace。
- 写 Agent 之前先问自己：**这个问题真的需要 Agent 吗？** 一个 prompt 能解决的不要套循环。
