## Day 8-9：读懂 ReAct 与 Agent 分界

### 目标

- 理解 augmented LLM、workflow、agent 的区别。
- 建立 ReAct 的最小心智模型：模型在循环里决定下一步，代码负责执行工具和维护状态。

### 阅读

- Anthropic Building Effective Agents。
- 本仓库 [03-核心概念](../../03-核心概念.md) 的 Agent、四层分界、ReAct 部分。

### 自测

- augmented LLM 和 Agent 有什么区别？
- Workflow 和 Agent 谁决定下一步？
- ReAct 和 Week1 Function Calling 差在哪？

### 关键结论

- ReAct 不是 Function Calling 的同义词。Function Calling 是协议，ReAct 是把协议放进循环后的控制结构。
- Workflow 的下一步由代码决定；Agent 的下一步由模型基于当前 state 决定。
- 不是所有“LLM + 工具”都应该叫 Agent。固定步骤能解决时，workflow 更稳定、更容易测试。

## Day 10-12：手写 ReAct 循环

### 目标

- 跑通 `react_agent.py`。
- 理解 `run_agent` 主循环、工具定义、dispatch、错误 observation。
- 验证天气 + 计算器 + 搜索的多步任务。

### 运行

```bash
cd ai-agent
source .venv/bin/activate
python week2-react-agent/code/react_agent.py
```

### 必须跑的用例

- 北京天气。
- 北京天气 + `23 * 47`。
- `100 / 0`。
- 订机票。

### 观察

- `messages` 如何从 `system → user` 变长。
- 每次 assistant 是否带 `tool_calls`。
- 每个工具结果如何写回 `role: tool`。
- 最后一条 assistant 为什么没有 `tool_calls`。

### 关键结论

- `messages` 是唯一状态，`assistant(tool_calls)` 和 `tool` observation 都必须按顺序追加。
- `max_steps` 是安全上限，不是正常结束条件。正常结束条件是模型不再返回 `tool_calls`。
- 一轮可能出现多个 `tool_calls`，每个工具结果都要带对应的 `tool_call_id` 写回。
- 工具异常不要直接让程序崩掉，应转成 observation，让模型决定重试或解释失败。

## Day 13-14：主动制造失败

### 目标

- 故意测试无工具、工具异常、步数不足、模型跳过工具等情况。
- 明确框架能帮什么，不能帮什么。

### 实验

- `max_steps=1`。
- 5 步以上长链任务。
- 同一轮多个工具调用。
- 要求“必须计算器算”，观察模型是否心算跳过。
- 问无合适工具的问题。

### 关键结论

- 模型可能心算跳过 calculator，这不是框架能天然解决的问题。
- 无合适工具时，Agent 应该承认能力边界，而不是编造执行结果。
- prompt、工具描述、工具权限、eval 用例要一起管理，单改 prompt 很容易治标不治本。
