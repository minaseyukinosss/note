# Week2 实验与踩坑

## 实验 1：`max_steps=1`

现象：模型可能只来得及发起工具调用，还没有机会基于 observation 总结最终回答。

结论：`max_steps` 是硬上限，不是“要走满的步骤数”。

## 实验 2：除以 0

期望：`calculator` 返回错误字符串，如“错误：除数不能为 0”。

不要让工具异常直接抛出到主循环，否则 Agent 没机会恢复或解释失败。

## 实验 3：无合适工具

问题示例：帮我订一张明天去上海的机票。

期望：模型礼貌说明无法完成，而不是编造航班。

如果模型编造，优先检查：

- system prompt 是否要求“不编造”。
- 工具 description 是否让模型误以为能订票。
- 是否应该把任务判定做成 workflow 前置分类。

## 实验 4：模型心算跳过工具

现象：用户要求“把气温加 10”，模型可能直接心算，不调用 `calculator`。

这说明 prompt 是软约束。若业务必须可审计，可选方案：

- system prompt 明确“所有算术必须调用 calculator”。
- 工具返回结构化数据，减少模型从自然语言里抠数字。
- 把流程改成 workflow：查天气后由代码强制调用 calculator。

## 实验 5：一轮多个 `tool_calls`

模型可能在同一轮同时请求天气和搜索。

处理原则：

- 先 append 带 `tool_calls` 的 assistant。
- 再按每个 call 追加对应 `tool` 消息。
- 每条 `tool` 都必须带对应 `tool_call_id`。

## 常见报错

| 现象 | 原因 / 修正 |
| --- | --- |
| API 报 tool 消息顺序错误 | assistant(tool_calls) 没有先 append |
| 模型第二轮不知道工具结果 | `role: tool` 缺失或 `tool_call_id` 错 |
| 工具参数解析失败 | `arguments` 不是合法 JSON，需捕获并返回错误 |
| 模型一直调同一个工具 | observation 不够清楚，或缺少停止提示 |
| 最终回答不完整 | trace 看是否某一步 observation 丢失 |

## 排错顺序

1. 打印完整 `messages`。
2. 找到第一处不符合预期的 assistant。
3. 看 tool name 是否正确。
4. 看 arguments 是否正确。
5. 看 observation 是否清楚。
6. 再决定改 prompt、工具、schema，还是改成 workflow。
