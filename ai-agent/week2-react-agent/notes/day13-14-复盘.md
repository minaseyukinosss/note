# Day 13-14：ReAct Agent 复盘

## 背景 / 学习目标

- 故意制造失败场景，观察 Agent 实际行为与预期差在哪。
- 回答三个问题：Agent 本质、裸写难点、希望框架解决什么。
- 为 Week3 LangGraph 重写做对比基线。

## 我跑了哪些挑战

| 场景 | 现象 |
| --- | --- |
| 5+ 步多工具链 | 4 轮循环完成：北京天气 → 上海天气 → 计算器 → 搜索 → 汇总，未死循环 |
| `max_steps=1` | 只够调一次 `get_weather`，返回「超过最大步数」，无最终回答 |
| 并行工具 | 「北京天气 + AI agent 是什么」一次返回两个 `tool_calls`，正常 |

## 关键细节：模型会「跳过工具」

用户要求：**先查北京天气，把返回的气温加 10**。

实际 trace 里，模型在 assistant 正文里直接写「北京气温 25°C，加 10 等于 **35**」，**没有调用 `calculator`**；后面「上海 25 × 35」才调了计算器。

这说明：

1. **Agent ≠ 严格按步骤走工具**。LLM 能心算时，可能认为不必调工具——对用户有时更快，对「必须可审计 / 可复现」的任务则是风险。
2. **Prompt 里的「请调用对应工具」是软约束**，不是硬保证；和 Workflow（代码写死先 A 再 B）不同。
3. **排错时要读 assistant 的 `content`**，不能只看有没有 `tool_calls`——「这一步算不算完成」可能藏在正文里。

若业务上**必须**走计算器，裸写阶段可尝试：

- 在 `SYSTEM_PROMPT` 里写死：「凡涉及算术，一律调用 `calculator`，禁止心算」；
- 工具返回结构化 JSON（如 `{"temp_c": 25}`），逼模型用表达式 `"25 + 10"` 而不是从自然语言里抠数字；
- 更硬的做法：Workflow 拆子任务（查天气 → 固定调 calculator），那就不是纯 Agent 了。

练习场景里心算 25+10 可以接受；上线前要清楚这是**可控性 trade-off**。

## 三个问题

### 1. Agent 本质是什么？

LLM 不会执行工具，只输出 `tool_calls`；我在 `for` 循环里执行工具、把结果塞回 `messages`，直到模型不再要工具。Agent = **augmented LLM + 动态循环**，路径由模型根据 observation 决定，不是代码写死的 if-else 链。

### 2. 裸写最难的部分？

- **`messages` 协议**：assistant 带 `tool_calls` 必须先 append，再 append 带 `tool_call_id` 的 `tool`；漏一步 API 就乱。
- **工具 observation 格式**：错误要变成字符串返回（如除零），不能抛异常打断循环。
- **不可控性**：选哪个工具、是否跳过工具、是否多轮重复——都靠 prompt + 模型，没有框架时全靠自己看 trace。

### 3. 希望框架帮我解决什么？

- 把「循环 + state（messages）+ 条件退出」收成 **node / edge**，少写样板代码。
- **Checkpointer**：跨轮对话恢复 state，不用自己管持久化。
- 框架**解决不了**：模型乱选工具、心算跳过 calculator——仍要靠 prompt、工具设计和 trace 排查。

## 小结

Week2 里程碑：能裸写 ReAct 循环，并能用 trace 解释「为什么这一步没调工具」。进入 Week3 时用 LangGraph 重写同一 Agent，对比代码量与上述「不可控」是否依旧存在。
