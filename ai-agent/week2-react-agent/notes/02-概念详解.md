# Week2 概念详解

## ReAct 是什么

ReAct = Reason + Act。经典论文里常写成：

```text
Thought → Action → Observation → Thought → ...
```

本仓库不用文本解析 `Thought:` / `Action:`，而是用现代 Function Calling 协议：

```text
assistant(tool_calls) → tool observation → assistant(tool_calls 或 final content)
```

循环语义一样，通信格式不同。

## 退出条件

ReAct 循环的正常退出条件是：

```text
本轮 assistant 没有 tool_calls，直接返回 content
```

`max_steps` 不是正常退出条件，只是防死循环的安全闸。触发 `max_steps` 通常说明任务没完成、工具选择不稳或 prompt 设计有问题。

## `messages` 是唯一状态

Week2 没有数据库、没有 LangGraph state，也没有长期记忆。所有上下文都在 `messages` 里。

典型多步结构：

```text
system
user
assistant(tool_calls: get_weather)
tool(weather observation)
assistant(tool_calls: calculator)
tool(calculation observation)
assistant(final content)
```

一轮 assistant 可以带多个 `tool_calls`，随后要追加多条 `tool` 消息。

## Tool description 是 Agent-Computer Interface

模型选择工具时主要看：

- 工具名。
- description。
- 参数 schema。
- 当前用户问题。
- 历史 observation。

description 写得差，模型就可能乱选、漏选或跳过工具。

## Workflow 和 Agent 的工程取舍

Agent 灵活，但代价是不可控。判断顺序：

1. 单次 prompt 能解决吗？
2. 固定步骤 workflow 能解决吗？
3. 步数、顺序、工具选择确实难提前写死吗？
4. 有 trace、eval、权限边界来承受不确定性吗？

只有后两项成立时，Agent 才更值得。

## 框架不能解决的事

框架能减少样板代码，但不能从根上解决：

- 模型心算跳过工具。
- 模型选错工具。
- 模型提前总结。
- 长链任务 compound errors。
- 工具 observation 本身不可信。

这些要靠 prompt、工具设计、workflow 拆分、评估和人工确认。
