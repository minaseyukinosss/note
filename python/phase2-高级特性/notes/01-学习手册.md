## Day 22：`self` + `__init__` + 类属性 vs 实例属性

### 学习目标

- 搞清 `self` 是什么、实例属性写在哪、类属性写在哪。
- 复现「可变类属性被所有实例共享」的坑。

### 关键观察与结论

#### 1. `self` 是什么？调用 `obj.method()` 时谁传给第一个参数？

**结论**：`self` 就是**当前实例**。写 `obj.method()` 时，Python 把 `obj` 自动传给方法的第一个参数；等价于 `Cls.method(obj)`。`__init__` 里用 `self.xxx = ...` 给**这个**实例挂数据。

#### 2. 类属性写在类体、实例属性写在 `__init__`——共享与独立分别怎么理解？

**结论**：**类属性**写在类体（如 `class C: x = 1`），类和所有实例默认共用一份。**实例属性**写在 `__init__`（如 `self.n = 0`），每个实例各自一份。Agent / session 状态必须用实例属性，避免串台。

#### 3. `class C: items = []` 再 `a = C(); b = C(); a.items.append(1)`，`b.items` 会怎样？为什么？

**结论**：`b.items` 也是 `[1]`，且 `a.items is b.items is C.items`。因为 `items = []` 是**可变类属性**，只创建一次、所有实例共享；`append` 原地修改同一 list。正确写法：在 `__init__` 里 `self.items = []`。与阶段一「可变默认参数」同类坑。

### 学了什么（能口述）

- `self` 是当前实例；`obj.method()` 等价于 `Cls.method(obj)`。
- 类属性写在类体、默认共享；实例属性写在 `__init__` 的 `self.xxx`，每实例一份。
- 可变类属性（`items = []`）会被所有实例共用；对象自己的状态必须在 `__init__` 里新建。

## Day 23：`@classmethod` / `@staticmethod`

### 学习目标

- 分清实例方法、类方法、静态方法的第一个参数与调用方式。
- 会用 `@classmethod` 做替代构造（如 `from_dict`）。

### 关键观察与结论

#### 1. `cls` 和 `self` 分别指向什么？`C.method()` 与 `c.method()` 都能调 classmethod 吗？

**结论**：`self` = **已经存在的那个实例**（要读/改它的数据时用实例方法）。`cls` = **类本身**（还没有实例、或要从别的格式「造出一个」时用 classmethod）。`Message.from_dict(...)` 和 `m.from_dict(...)` 都能调 classmethod；关键是自动传入的 `cls` 是「调用时的类」。

#### 2. `@staticmethod` 和普通函数放在模块顶层，选用标准是什么？

**结论**：静态方法**不接收** `self`/`cls`，和模块里的普通函数能力相同。只有想把名字挂在类下面（`Message.is_valid_role`）图个命名空间时才用；多数情况直接写模块函数更清晰。学它主要是为了读别人/框架代码时不懵。

#### 3. Agent 里 `Tool.from_function(...)` / `Model.from_config(...)` 更像哪种方法？

**结论**：**classmethod（工厂）**。输入不是 `__init__` 的原始参数（而是函数、配置 dict、JSON），先转换再 `cls(...)` 造实例。实例方法则是造好之后的行为，如 `tool.run(query)`、`agent.reply(msg)`。

#### 4. 「从 dict / 配置造一个」是什么意思？

**结论**：手里已有数据（API/JSON/配置，常是 dict），但还没有该类的实例，要把这份数据**翻译成对象**。例如 `data = {"role": "user", "content": "hi"}` 只是 dict；`Message.from_dict(data)` 才得到 `Message` 实例。和手写 `Message(data["role"], data["content"])` 结果一样，只是拆字段的步骤藏进类里。

#### 5. 类方法工厂造对象时会不会走 `__init__`？

**结论**：会。工厂里写 `cls(...)` 或 `Message(...)`，和直接 `Message("user", "hi")` 一样，会进对应类的 `__init__`。工厂**不是绕过** `__init__`，而是先把 dict/配置拆成 `__init__` 要的参数，再照常初始化。例外：工厂若返回缓存里已有的实例、或不调用 `cls(...)`，才不一定再进 `__init__`。

#### 6. 为什么工厂里写 `cls(...)` 而不是写死 `Message(...)`？子类没写 `from_dict` 为什么还能调？

**结论**：子类会**继承**父类的 classmethod，所以 `ToolMessage` 没写 `from_dict` 也能 `ToolMessage.from_dict(...)`；调用时传入的 `cls` 是 **`ToolMessage`**。写 `cls(...)` 就会造出子类实例；写死 `Message(...)` 则子类调用也会得到父类实例，子类白继承了。

### 学了什么（能口述）

- 类里三种方法：**实例方法**吃 `self`（已有对象要干活，如 `tool.run`）；**类方法**吃 `cls`（还没有对象、从 dict/配置造一个，如 `Message.from_dict`）；**静态方法**谁都不吃（和模块函数几乎一样，自己写优先用模块函数）。
- 「从 dict 造」= 把现成字典翻译成对象；工厂里 `cls(...)` **仍会走 `__init__`**，不是绕过。
- 工厂写 `cls(...)` 不写死类名：子类能继承 `from_dict`，调用时 `cls` 是子类，才能造出子类实例。

## Day 24：单继承 + `super()`

### 学习目标

- 会写子类 `__init__` 并正确调用 `super().__init__(...)`。
- 理解方法查找：子类没有就去父类找。

### 关键观察与结论

#### 1. 子类重写 `__init__` 却不调 `super().__init__`，父类属性会怎样？

**结论**：父类 `__init__` **不会自动跑**，父类负责的字段（如 `name`、`species`）不会出现，访问会 `AttributeError`。子类一旦自己写了 `__init__`，就要自己喊 `super().__init__(...)` 把父类那部分初始化做完，再设子类字段。

#### 2. `super().method()` 查找的是「父类」还是「MRO 里的下一个」？单继承时两者一样吗？

**结论**：严格说是 **MRO 里的下一个**（Day 25）。**单继承时两者一样**：`super()` 就是那个唯一父类。今天够用的记法：`super().__init__(...)` = 去跑父类的 `__init__`。

#### 3. 子类不重写 `__init__` 会怎样？

**结论**：创建实例直接用父类 `__init__`，父类字段都有；构造参数也跟父类一样。没有地方接收子类额外字段（如 `breed`），所以也没有该属性。三种选择：不写 = 全跟父类；写了不 `super()` = 丢掉父类字段；写了且 `super()` = 两边字段都有。O3 的 `EchoTool` 属于第三种：没有新字段，但要把 `name` 固定成 `"echo"`，所以仍 `super().__init__("echo")`。

### 学了什么（能口述）

- 子类没写的方法会去父类找（继承）；写了同名方法就盖住父类（覆盖）。
- 子类自己写了 `__init__`，父类 `__init__` 不会自动执行，必须 `super().__init__(...)`。
- 不写子类 `__init__`：只有父类字段；需要额外状态或固定父类参数时，才自己写并先 `super()`。
- 单继承里 `super()` 就是父类。

## Day 25：多继承 + MRO

### 学习目标

- 能用 `Cls.__mro__` 读出方法解析顺序。
- 理解多继承下 `super()` 按 MRO 前进，不是「只找直接父类」。

### 关键观察与结论

#### 1. 打印 `SomeClass.__mro__`，顺序怎么读？查找停在哪？

**结论**：从左到右就是查找顺序。`class D(B, C)` 时是 `D → B → C → A → object`：自己 → 括号里先写的父类 → 后写的父类 → 共同祖先 → 终点 `object`。找方法时清单上**第一个有该方法的类**就停；一路没有就到 `object`。

#### 2. 钻石继承（D→B、D→C、B→A、C→A）时，`A.__init__` 会被调用几次？靠什么机制？

**结论**：大家都写 `super().__init__()` 时，**只一次**。`super()` 走的是 **MRO 上下一个**，不是「括号里的父类」：`B` 的 `super()` 会到 `C` 而不是直接到 `A`，最后才到 `A`，所以 `A` 不会被 B、C 各调一次。若写成 `A.__init__(self)` 而不是 `super()`，`A` 就可能跑两次。

#### 3. 框架长继承链（如 `BaseModel` 子类）为什么要关心 MRO？

**结论**：方法到底用的是哪一层、`super()` 下一站是谁，都由 MRO 决定。读源码时打印 `Cls.__mro__`，能看清「我调的方法实际定义在哪个类」。自己写多继承时，每个 `__init__` 都 `super()`，才不会把链截断。

#### 4. `object.__init__` 是什么？A 里 `super().__init__()` 必写吗？

**结论**：MRO 最后是 `object`；`object.__init__` 是内置空收尾，几乎什么都不做。A 的 `super().__init__()` 就是把接力棒交给它。钻石里 A 后面只有 `object` 时，A 不写也能跑；多继承仍建议**每个 `__init__` 都写**，以免以后 MRO 在 A 后面还插入别的类时链断掉。

### 学了什么（能口述）

- MRO 是一张固定查找清单，`Cls.__mro__` 从左到右读。
- 多继承时 `super()` = 清单上下一个，不一定是括号里写的父类。
- 钻石里人人 `super()`，共同祖先的 `__init__` 只跑一次。
- `object.__init__` 是空收尾；最顶用户类可以不写 `super()`，多继承习惯上仍写。

## Day 26：`ABC` + `@abstractmethod`

### 学习目标

- 会定义抽象基类；未实现抽象方法的子类不能实例化。
- 理解「名义子类型」：必须显式继承 ABC 才算实现接口。
- 分清：抽象类**可以**有 `__init__` 和普通实例方法；不能的是「抽象方法没补完就 `类名()`」。

### 关键观察与结论

#### 1. 继承 ABC 但漏实现 `@abstractmethod`，`Sub()` 会怎样？

**结论**：报 **`TypeError`**（`Can't instantiate abstract class ... with abstract methods ...`），对象造不出来。抽象类自己 `BaseMemory()` 同样是这个错。这和 Day 24 `raise NotImplementedError` 不同：那种是对象能造、调用时才炸；ABC 是 **`类名()` 这一步就拦**。

#### 2. ABC 解决什么问题？和「只写文档约定接口」比有什么好处？

**结论**：规定「所有 Memory 必须有 `add`/`get`」时，只写在注释里会漏实现却发现不了。ABC + `@abstractmethod` 在实例化时检查。**必须显式继承才算实现接口** = 要被当成「实现了 `BaseMemory`」，定义时必须写 `class Xxx(BaseMemory)`；不写继承、哪怕自己也有 `add`/`get`，也不算。这叫名义子类型（按族谱认，不按长得像）。

#### 3. 抽象类是不是没有 `__init__`、没有实例方法？（易混）

**结论**：不是。抽象类可以有 `__init__`，也可以有已经写完的普通方法，子类照样继承 / `super()`。`@abstractmethod` 只是「必须由子类补的洞」。不能 `BaseMemory()` 是因为还有洞没补，不是因为抽象类禁止构造和方法。O5 的 `BaseMemory` 两个方法都是洞，所以看起来像什么都没有，那是题目写得精简。

#### 4. `ListMemory` 里为什么能用 `self._items`？名字能改吗？

**结论**：`_items` 是子类 `__init__` 里自己挂到这个实例上的属性，和 Day 22 的 `self.n` 一样；`add`/`get` 里的 `self` 是同一个对象。名字可改成 `_list` 等，同一类里前后一致即可。`_` 前缀只是「内部用」约定，不是 ABC 给的权限，父类也不必声明这个属性。`get` 返回 `.copy()` 是为了外面改 list 不影响内部。

### 学了什么（能口述）

- ABC + `@abstractmethod`：规定子类必须实现的方法；没补完就不能 `类名()`，报 `TypeError`。
- 抽象类可以有 `__init__` 和普通方法；禁止的是「还有抽象方法就实例化」。
- 必须写 `class Xxx(BaseMemory)` 才算实现这个接口；光有同款 `add`/`get` 不算。
- 子类实例属性自己在 `__init__` 里起名并挂上，`self` 在各方法间共享。

## Day 27：`Protocol`（结构化子类型）

### 学习目标

- 理解 Protocol：长得像就行，不必显式继承。
- 能说清 ABC vs Protocol 何时选用。

### 关键观察与结论

#### 1. 一个类没继承某 Protocol，但有同名方法——类型检查器认不认？运行时呢？

**结论**：类型检查器**认**（长得像就行，不必写 `class Xxx(RunnableLike)`）。运行时默认**不按 Protocol 拦**：`FakeChain()` 能造，`isinstance(FakeChain(), RunnableLike)` 一般为 `False`；真缺 `invoke` 要等到调用那一行才 `AttributeError`。和 ABC 对比：ABC 必须写 `(BaseMemory)` 才算实现接口，且还有洞就不能 `()`。

#### 2. 框架里 `Runnable` / 可调用对象更常靠 ABC 还是 Protocol？各自适合什么？

**结论**：两种都用。**ABC**：自己的继承树、要运行时拦住没写完的子类、基类里要放公共代码（如 `BaseMemory`）。**Protocol**：不管对方写不写继承，只要求有某些方法（如有 `invoke` 就算可跑）。本环境未装 Pylance/Cursor Pyright，编辑器红线演示跳过；检查器会报的内容和 `run(NotRunnable())` 运行时缺方法是同一件事，只是提前画出来。

### 学了什么（能口述）

- Protocol：不写继承，只要方法长得像，类型检查器也可以认。
- 默认不管运行时实例化；缺方法是调用时才炸，不是 `类名()` 就 `TypeError`。
- ABC 认户口本（必须写父类）；Protocol 认长得像。自己的树 + 要运行时拦住 → ABC；不管对方继不继承 → Protocol。
