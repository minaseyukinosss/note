### Day 2 — 可变 vs 不可变 + 参数传递

- 记录：写 3 句话解释"Python 传参到底传的是什么"。

1. Python 传参传的是对象的引用（可以理解成「贴标签」），不是把整个对象拷贝一份。
2. 函数里对可变对象做原地修改（`append`、`pop`、`d[k]=v`），调用方手里的**同一个**对象也会变。
3. 对不可变对象（`int`、`str`、`tuple`），赋值只会让局部变量指向新对象，不会改变调用方原来的那个。

## Week 2：函数与作用域（Day 8-14）



### Day 8 — 默认参数 + 关键字参数

- [x] 学：位置参数 vs 关键字参数、`def f(a, b=1, *, c)`（`*` 后强制关键字）。
- [x] 实验：调用 `f(1, c=3)`，感受关键字参数可读性。

- 记录：强制关键字参数对"清晰的工具函数接口"有什么好处？
  1. 调用时必须写参数名（如 `temperature=0.7`），代码自解释，不用查函数签名猜位置。
  2. 多个同类型参数（`int`、`str`）时避免传反，Agent 里 `model`、`temperature`、`max_tokens` 这类参数尤为需要。
  3. 以后给函数加参数时，已有 `keyword=...` 调用不受影响，接口演进更安全。


### Day 9 — 可变默认参数陷阱（重点）

- [x] 实验：写 `def bad(x, acc=[]): acc.append(x); return acc`，连续调 3 次看输出。
- [x] 做题 **6** `append_log`（用 `None` 哨兵的正确写法），跑通。

- 记录：为什么默认值只求值一次？这在 Agent 状态共享里会怎么埋 bug？
  1. 默认参数在**函数定义时**求值并存入 `__defaults__`，不是每次调用时重新创建。
  2. `acc=[]` 时所有省略该参数的调用共用同一 list，`.append` 会跨调用累积（`bad(1)`→`[1]`，`bad(2)`→`[1,2]`）。
  3. Agent 里 `history=[]`、`messages=[]` 等默认值会让不同会话/请求共享状态，出现 tool 调用历史串台、多用户数据污染等难查 bug。正确写法：`None` 哨兵 + 函数内 `if logs is None: logs = []`。


### Day 10 — `*args` / `**kwargs`

- [x] 学：`*args` 收集位置参数、`**kwargs` 收集关键字参数、`func(*list, **dict)` 展开透传。
- [x] 做题 **7** `call_with_defaults`，跑通。

- 记录：框架源码里到处是 `**kwargs`，它解决了什么问题？
  1. **参数数量不确定**：底层 API 参数多且会变（`model`、`temperature`、`stream`…），用 `**kwargs` 全收，不用每次改函数签名。
  2. **透传不丢失**：包装层只需 `return real(*args, **kwargs)`，调用方传什么，底层就收到什么。
  3. **扩展性**：框架加新参数时，旧包装函数不用改——`**kwargs` 自动接住新关键字。
  - 补充：Agent / SDK 场景里 `**kwargs` 是主角；`*args` 多在装饰器、完整透传 `func(*args, **kwargs)`、展开调用 `f(*items)` 里当配角，日常显眼度低但别忽略。


### Day 11 — 作用域 LEGB

- [x] 学：Local → Enclosing → Global → Builtin 查找顺序；`global` / `nonlocal`。
- [x] 实验：函数内改全局变量不加 `global` 会怎样？

- 记录：LEGB 一句话总结。
  Python 找名字从当前函数（Local）→ 外层函数（Enclosing）→ 模块顶层（Global）→ 内置（Builtin）逐级向外；函数内一旦赋值就创建 Local 变量，改 Global 须 `global`，改外层嵌套变量须 `nonlocal`。

  
### Day 12 — 闭包

> 疑问汇总：[`04-闭包与作用域-qa.md`](./04-闭包与作用域-qa.md)

- [x] 学：闭包捕获的是变量（不是值）；`nonlocal` 的作用。
- [x] 做题 **8** `make_counter`，跑通。
- [x] 进阶实验：循环里创建闭包 `[lambda: i for i in range(3)]` 全返回 2，理解晚绑定坑。

- 记录：闭包和装饰器的关系（为阶段二铺垫）。
  - **闭包**：内层函数引用外层变量，外层 `return` 后内层仍能访问/修改那个变量（如 `make_counter` 里的 `count`）。
  - **`nonlocal`**：内层要**改**外层变量时用；只读不用加。不加则 `count += 1` 会 `UnboundLocalError`。
  - **`return counter`**：把内层函数交出去，外面才能反复调用；`count` 变 1、2、3 是因为**调用** `c()`，不是因为 `return` 本身。
  - **晚绑定坑**：`[lambda: i for i in range(3)]` 三个 lambda 捕获**同一个** `i`，调用时 `i` 已是 2 → 全返回 2。修复：`lambda i=i: i` 用默认参数冻结当前值。
  - **与装饰器**：装饰器本质是「接受函数、返回新函数」的闭包；`@decorator` 等价于 `func = decorator(func)`，阶段二会正式学。

## Week 3：异常与模块 + CLI 实战（Day 15-21）



### Day 15 — try/except/else/finally

- [x] 学：`try/except/else/finally` 各段何时执行；捕获具体异常而非裸 `except`。
- [x] 实验：`int("abc")` 抛什么异常？捕获它并打印友好信息。
- [x] 做题 **11** `safe_int`，跑通。

- 记录：`else` 和 `finally` 分别放什么代码？
  - **`else`**：只有 `try` 没出异常才执行；放「解析/转换成功后」的后续逻辑（如 `process(result)`），不放可能出错的代码。
  - **`finally`**：无论如何都执行；放清理资源（关文件、关连接、释放锁）。即使 `try` 里 `return` 也会先跑 `finally`。
  - **捕获习惯**：写具体异常如 `ValueError`，不写裸 `except`；`int("abc")` 抛 `ValueError` 不是 `TypeError`。



### Day 16 — 自定义异常 + EAFP

- [x] 学：EAFP（先做了再说，错了再 except）vs LBYL（先 if 检查再操作）；`class MyError(Exception)`。
- [x] 练习：写一个 `parse_int(s)`，失败时 `raise MalformedLineError`。
- [x] 做题 **12** `parse_int`，跑通。

- 记录：

  **EAFP 和 LBYL 分别是什么？**

  | 缩写 | 全称 | 中文 | 做法 |
  | --- | --- | --- | --- |
  | **LBYL** | Look Before You Leap | 先查再跳 | 先 `if` 判断条件安全，通过了再操作 |
  | **EAFP** | Easier to Ask Forgiveness than Permission | 先做了再说 | 直接操作，出异常再 `except` 处理 |

  同一任务两种写法（取 dict 的 key）：
  - LBYL：`if "timeout" in d: value = d["timeout"] else: value = 30`
  - EAFP：`try: value = d["timeout"] except KeyError: value = 30`
  结果一样；差别在**习惯与场景**，不是谁永远更对。

  **为什么 Python 更常用 EAFP？**
  1. 标准库设计就是「不对就抛异常」——`dict[k]`、`int(s)`、`json.loads(s)` 失败时抛异常，不是返回错误码；跟着库写 try/except 更自然。
  2. 成功路径干净：LBYL 每层都要 `if err: return`；EAFP 的 `try` 块只写 happy path。
  3. LBYL 自己写检查往往不全：如 `s.isdigit()` 漏掉 `"-3"`、`" 42 "`；直接 `int(s)` 让标准库判断更可靠。

  **什么时候用 LBYL？**
  - 条件简单、且不会和操作重复：`if x is None:`、`if not messages:` 再往下走。
  - 同一层逻辑别混写：不要又 `if key in d` 又 `try/except KeyError` 写两遍。

  **和今天练习的关系**
  - `safe_int`、`parse_int` **都是 EAFP**（`try int(s)`）；差别在 `except` 里返回 default 还是 `raise MalformedLineError`。
  - 可选字段 → `safe_int` 返回 default；必须合法 → `parse_int` raise，供 Day 21 CLI 跳过坏行并计数。
  - `raise ... from e`：包装异常时保留原因链，调试能看到 `MalformedLineError ← ValueError`。

  **为什么 Python 用异常而不是返回错误码？**

  先分清两种风格长什么样（Go / C 常见错误码，Python 不这么写）：

  ```python
  # 错误码风格（伪代码）：函数返回 (结果, 错误)
  n, err = parse_int("abc")
  if err is not None:
      return err
  total = n + 10

  # 异常风格（Python 惯用法）：失败就 raise，成功才继续
  n = parse_int("abc")   # "abc" 会直接抛 MalformedLineError，下面一行不会执行
  total = n + 10
  ```

  **1. 错误码必须「每层都检查」，漏查就静默出错**

  ```python
  n, err = parse_int("abc")
  # 忘了写 if err —— 程序不会崩，但 n 可能是 None / 0
  total = n + 10          # 算出错误结果，难排查

  n = parse_int("abc")    # 未捕获时立刻抛异常 + 完整 traceback，停在出错行
  ```

  错误码把责任推给**每个调用方**「记得检查」；异常把责任交给**一处** `try/except`（通常在入口或边界），漏写更容易在测试/运行时暴露。

  **2. 错误码让「正常逻辑」和「错误处理」缠在一起**

  读 JSONL 并统计，错误码写法每层都要 `if err: return err`：

  ```python
  data, err = read_file(path)
  if err: return err
  records, err = parse_all(data)
  if err: return err
  stats, err = count_by_level(records)
  if err: return err
  ```

  异常写法：中间函数只管业务，失败自动往上冒；**只在入口**统一处理：

  ```python
  try:
      data = read_file(path)
      records = parse_all(data)
      stats = count_by_level(records)
  except FileNotFoundError:
      print("文件不存在")
  except MalformedLineError as e:
      print(f"格式错误: {e}")
  ```

  正常路径不被 `if err` 打断，读代码时先读 `try` 块就能看懂主流程。

  **3. 错误码向上传递要手动「一层层 return err」**

  `parse_line` 失败 → `read_lines` 要 `return err` → `main` 再检查。三层就要写三遍传播逻辑。

  异常：`parse_line` 里 `raise`，栈自动 unwind 到**第一个**匹配的 `except`；中间层不必每个函数都带 `err` 参数或返回值。

  **4. 错误码难以「只处理某一类错误」**

  Day 21 CLI：坏行跳过、其他 bug 仍要暴露。

  ```python
  for line in lines:
      try:
          record = parse_line(line)
      except MalformedLineError:
          bad_count += 1
          continue
      process(record)
  # KeyError、TypeError 等不会被上面 except 吞掉，继续往上抛 → 真 bug 不会被当成「坏行」
  ```

  错误码若统一返回 `ERR_PARSE`，调用方很难区分「可跳过的坏行」和「程序写错了」；异常用**类型**（`MalformedLineError` vs `ValueError`）分层捕获。

  **5. 和 EAFP 是一套的**

  标准库 `int(s)`、`json.loads(s)` 失败时**只抛异常、不返回 err**。若上层用错误码风格，就得在每个调用点包一层转换，反而别扭。Python 选异常，是为了和「先做了再说、错了再 except」的 EAFP 一致。

  **一句话**：错误码 = 每个调用点都要检查、手动传播；异常 = 成功路径连续写、失败在边界统一处理，且漏处理更容易立刻暴露。



### Day 17 — 模块与 import

- [x] 学：`import` 是运行时执行的；`import x` vs `from x import y`；`if __name__ == "__main__"`。
- [x] 实验：新建两个 `.py` 文件互相 import，制造一次循环导入报错并理解。

- 记录：为什么说"import 是运行时执行的"？循环导入为什么会炸？
  - **运行时 import**：解释器执行到 `import foo` 才加载并跑 `foo.py` 顶层代码；同一进程重复 import 用 `sys.modules` 缓存，顶层只执行一次（实验二里 `[math_utils]` 只打印一次）。
  - **`__name__`**：解释器原生设定；`python greet.py` → `"__main__"`，`import greet` → `"greet"`。CLI 入口放 `if __name__ == "__main__":`，避免被 import 时误跑副作用。
  - **两种 import**：`import math_utils` 要写成 `math_utils.add()`（带前缀、好认来源）；`from math_utils import multiply` 直接写 `multiply()`（短、但要往上翻才知道从哪来）。
  - **循环导入**：A 顶层 import B、B 顶层又 import A → A 还没定义完就被 B 要名字 → `partially initialized module`。打破环：抽第三模块，或函数内延迟 import（`module_b_lazy`）。



### Day 18 — 包与相对导入

- [x] 学：`__init__.py`、包 vs 模块、相对导入 `from .foo import bar`。
- [x] 练习：为下面的 CLI 项目建好目录：`logtool/` 下放 `__init__.py`、`parser.py`、`stats.py`、`__main__.py`。

- 记录：`src/` 布局的好处（阶段三会正式学）。
  - **包 vs 模块**：`.py` 是模块；带 `__init__.py` 的目录是包。`__init__.py` 可汇总对外 API（`from .parser import ...`）。
  - **相对导入**：包内 `from .parser import X`，`.` = 当前包 `logtool`。必须作为包成员加载（`python -m logtool`）；`python logtool/__main__.py` → `no known parent package`。
  - **`python -m logtool`**：以包名加载，执行 `__main__.py`，等价于 Day 17 的入口保护，但是包级。
  - **`src/` 布局**：源码进 `src/logtool/`，根目录放配置/测试，减少「当前目录同名文件夹误被 import」和与已安装包混淆（阶段三用 uv 时会正式搭）。
